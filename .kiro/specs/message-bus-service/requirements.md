# Requirements Document

#[[file:.kiro/specs/_global/requirements-shared.md]]

## Introduction

Message Bus Service — a two-sided communication layer spanning both the Angular frontend and .NET backend. All inter-layer messaging routes through this service instead of direct `window.external.sendMessage` / `receiveMessage` calls. Either side can initiate messages: the frontend sends requests with unique correlation IDs and receives correlated responses, and the backend can push unsolicited messages to the frontend. Supports multiple message types, queuing of same-type messages, a "latest wins" mode that discards queued messages of the same type when a newer one arrives, and priority-based dispatch with arrival-order tiebreaking across queues.

## Glossary

- **Message_Bus**: The combined communication service spanning both Angular frontend (Message_Bus_Client) and .NET backend (Message_Bus_Host)
- **Message_Bus_Client**: The Angular injectable singleton service — queues outbound messages, dispatches them to the bridge, and routes inbound responses to callers
- **Message_Bus_Host**: The .NET backend service — receives messages from the bridge, routes them to registered handlers, sends responses back, and can initiate unsolicited messages to the frontend
- **Message_Type**: A string identifier categorizing a message (e.g. `"open-file"`, `"file-content"`)
- **Correlation_ID**: A unique string identifier generated per outbound request, used to match a response back to the originating request
- **Message_Queue**: An ordered collection of pending outbound messages of a given Message_Type
- **Queue_Mode**: The queuing strategy for a Message_Type — either "accumulate" (queue all) or "latest-wins" (discard older, keep newest)
- **Outbound_Message**: A message sent from one side to the other via Message_Bridge, containing Message_Type, Correlation_ID, and optional payload
- **Inbound_Message**: A message received from the other side via Message_Bridge, containing Message_Type, Correlation_ID, and optional payload
- **Backend_Push**: An unsolicited message initiated by Message_Bus_Host and sent to Message_Bus_Client without a prior frontend request — uses its own Correlation_ID generated by the backend
- **System_Message**: A message with a reserved Message_Type prefix `"system:"` (e.g. `"system:error"`, `"system:alert"`) — always processed at High priority regardless of configuration, delivered even without explicit Subscribers
- **Fallback_Handler**: A single catch-all handler registered on Message_Bus_Client that receives any Inbound_Message whose Message_Type has no registered Subscribers and is not a System_Message
- **Subscriber**: A component or service registered to receive Inbound_Messages of a specific Message_Type
- **Handler**: A .NET function registered on Message_Bus_Host to process incoming messages of a specific Message_Type
- **Priority**: A predefined level assigned per Message_Type determining dispatch order. Three levels: High (0), Normal (1), Low (2) — lower numeric value = higher dispatch priority
- **Arrival_Timestamp**: A monotonically increasing sequence number assigned to each outbound message when it enters the Message_Bus_Client, used to determine dispatch order among queues of equal Priority
- **Dispatch_Order**: The sequence in which queued outbound messages are transmitted to the Message_Bridge, determined first by Priority then by Arrival_Timestamp

## Requirements

### Requirement 1: Service Registration and Lifecycle

**User Story:** As a developer, I want a two-sided message bus (frontend client + backend host), so that communication is centralized, correlation-tracked, and testable on both sides.

#### Acceptance Criteria

1. THE Message_Bus_Client SHALL be provided as a singleton Angular injectable service available application-wide
2. WHEN the Message_Bus_Client is instantiated, THE Message_Bus_Client SHALL register a callback via the Message_Bridge inbound channel (`window.external.receiveMessage`) to receive all backend-originated messages
3. THE Message_Bus_Client SHALL expose a method to send a request with a Message_Type and optional payload, which generates a unique Correlation_ID and returns it to the caller
4. THE Message_Bus_Client SHALL expose a method to subscribe to responses by Message_Type, delivering the Correlation_ID and payload to the subscriber when a matching response arrives
5. WHEN the Application is destroyed, THE Message_Bus_Client SHALL unregister the Message_Bridge callback and complete all exposed observable streams so that active subscribers receive a completion notification
6. THE Message_Bus_Host SHALL be a .NET service instantiated at application startup that registers a `WebMessageReceived` handler on the Photino_Window
7. THE Message_Bus_Host SHALL allow registering Handler functions per Message_Type to process incoming requests
8. WHEN the Message_Bus_Host receives a message from the bridge, THE Message_Bus_Host SHALL parse the Message_Type and Correlation_ID, invoke the registered Handler, and send the response back via `SendWebMessage` with the same Correlation_ID
9. THE Message_Bus_Host SHALL expose a method to send unsolicited messages (Backend_Push) to the frontend with a Message_Type, a backend-generated Correlation_ID, and optional payload
10. WHEN the Message_Bus_Client receives a Backend_Push (a message whose Correlation_ID does not match any pending frontend request), THE Message_Bus_Client SHALL deliver it to Subscribers registered for that Message_Type

### Requirement 2: Sending Messages (Frontend → Backend)

**User Story:** As a developer, I want to send typed messages with correlation IDs to the backend through the Message_Bus_Client, so that responses can be matched to their originating requests.

#### Acceptance Criteria

1. WHEN a component calls the send method with a Message_Type and optional payload, THE Message_Bus_Client SHALL generate a unique Correlation_ID, encode the message (Message_Type + Correlation_ID + payload), and enqueue it for dispatch
2. THE Message_Bus_Client SHALL return the generated Correlation_ID to the caller so the caller can match the future response
3. THE Message_Bus_Client SHALL support sending messages with a string payload or with no payload (command-only)
4. THE Message_Bus_Client SHALL treat no-payload and empty-string payload as equivalent — both encode identically on the wire
5. THE Message_Bus_Client send method SHALL be non-blocking — it SHALL return the Correlation_ID immediately without waiting for backend response
6. IF the Message_Bridge throws an error during transmission, THEN THE Message_Bus_Client SHALL catch the error and discard the message without propagating the exception to the caller — the Correlation_ID already returned to the caller remains valid but will never receive a response (timeout will eventually fire)
7. THE Message_Bus_Client SHALL only discard messages due to Message_Bridge transmission errors — other error conditions (validation failures, capacity overflow) SHALL follow their own defined error policies

### Requirement 3: Receiving Responses (Backend → Frontend)

**User Story:** As a developer, I want to subscribe to typed responses and have them correlated to my original request, so that I know which response belongs to which request.

#### Acceptance Criteria

1. THE Message_Bus_Client SHALL allow Subscribers to register for responses by Message_Type and SHALL return a subscription handle that can be used to unregister
2. WHEN a Subscriber unregisters using its subscription handle, THE Message_Bus_Client SHALL stop delivering responses of that Message_Type to that Subscriber
3. WHEN an Inbound_Message arrives from the Message_Bridge, THE Message_Bus_Client SHALL parse the Correlation_ID and deliver the payload along with the Correlation_ID to all Subscribers registered for that Message_Type
4. WHEN an Inbound_Message arrives with a Message_Type that has no registered Subscribers and is not a System_Message, THE Message_Bus_Client SHALL route the message to the Fallback_Handler if one is registered, or discard silently if no Fallback_Handler is registered
5. IF a Subscriber throws an error during message handling, THEN THE Message_Bus_Client SHALL continue delivering the same Inbound_Message to remaining Subscribers registered for that Message_Type
6. THE Message_Bus_Client SHALL deliver Inbound_Messages asynchronously via microtask scheduling (e.g. `Promise.resolve().then(...)` or `queueMicrotask`) so that the Message_Bridge listener returns immediately; per-Message_Type delivery order SHALL be preserved (messages of the same type delivered in arrival order)

### Requirement 4: Message Queuing — Accumulate Mode

**User Story:** As a developer, I want to queue multiple messages of the same type, so that none are lost when the backend is busy processing earlier messages.

#### Acceptance Criteria

1. WHILE Queue_Mode for a Message_Type is set to "accumulate", THE Message_Bus_Client SHALL enqueue each outbound message of that Message_Type in FIFO order, assigning each message an Arrival_Timestamp at enqueue time
2. WHEN the dispatcher selects this queue for transmission, THE Message_Bus_Client SHALL transmit the oldest (front) message and remove it from the queue
3. THE Message_Bus_Client SHALL preserve all enqueued messages until they are transmitted, up to a maximum of 100 messages per Message_Type
4. IF the Message_Queue for a Message_Type reaches exactly 100 messages, THEN THE Message_Bus_Client SHALL discard the newest incoming message and retain the existing queued messages — no early discard threshold or in-transit accounting SHALL be applied

### Requirement 5: Message Queuing — Latest-Wins Mode

**User Story:** As a developer, I want a mode where only the most recent message of a type is kept, so that stale queued messages are automatically discarded when a newer one arrives.

#### Acceptance Criteria

1. WHILE Queue_Mode for a Message_Type is set to "latest-wins", THE Message_Bus_Client SHALL retain only the most recently enqueued outbound message of that Message_Type in the Message_Queue, replacing any previously queued message of the same Message_Type
2. WHEN a new outbound message of a Message_Type configured as "latest-wins" is enqueued, THE Message_Bus_Client SHALL atomically discard all previously queued messages of that same Message_Type, store only the new message, and update the queue's Arrival_Timestamp to the new message's Arrival_Timestamp
3. WHEN the dispatcher selects a "latest-wins" queue for transmission, THE Message_Bus_Client SHALL send the single stored message and remove it from the Message_Queue
4. IF the Message_Bus_Client attempts to transmit from a "latest-wins" queue that contains no messages, THEN THE Message_Bus_Client SHALL perform no transmission and SHALL NOT produce an error

### Requirement 6: Queue Mode Configuration

**User Story:** As a developer, I want to configure the queuing strategy per message type, so that each communication channel behaves appropriately for its use case.

#### Acceptance Criteria

1. THE Message_Bus_Client SHALL support exactly two Queue_Mode values: "accumulate" and "latest-wins"
2. THE Message_Bus_Client SHALL allow Queue_Mode and Priority to be configured per Message_Type at registration time only — runtime reconfiguration after the first message of that type is enqueued SHALL NOT be permitted
3. WHILE a Message_Type is configured with "accumulate" Queue_Mode, THE Message_Bus_Client SHALL retain all sent messages in sending order for delivery
4. WHILE a Message_Type is configured with "latest-wins" Queue_Mode, THE Message_Bus_Client SHALL retain only the most recently sent message, discarding any previously queued undelivered messages for that Message_Type
5. IF a Message_Type is sent without prior Queue_Mode configuration, THEN THE Message_Bus_Client SHALL apply the "accumulate" mode with default Priority Normal (1) for that Message_Type
6. IF a caller attempts to configure a Queue_Mode value other than "accumulate" or "latest-wins", THEN THE Message_Bus_Client SHALL reject the configuration and indicate an error

### Requirement 7: Priority-Based Dispatch

**User Story:** As a developer, I want messages dispatched in priority order with arrival-time tiebreaking, so that high-priority commands are sent before lower-priority ones while preserving fairness within the same priority level.

#### Acceptance Criteria

1. THE Message_Bus_Client SHALL define exactly three Priority levels: High (0), Normal (1), and Low (2), and SHALL allow one of these levels to be configured per Message_Type at registration time
2. THE Message_Bus_Client SHALL assign a monotonically increasing Arrival_Timestamp to each outbound message at the moment it is accepted into the Message_Bus_Client
3. WHEN the Message_Bus_Client selects the next message to transmit, THE Message_Bus_Client SHALL choose the message from the queue with the lowest (highest-priority) Priority value that has a message ready to send
4. WHEN multiple queues share the same Priority value and each has a message ready to send, THE Message_Bus_Client SHALL transmit the message whose front-of-queue entry has the earliest Arrival_Timestamp
5. FOR a "latest-wins" queue, THE Arrival_Timestamp used for dispatch ordering SHALL be the Arrival_Timestamp of the most recent message (the one that replaced all previous messages in that queue)
6. IF a Message_Type is registered without an explicit Priority, THEN THE Message_Bus_Client SHALL assign a default Priority of Normal (1)
7. THE Message_Bus_Client SHALL dispatch messages sequentially — it SHALL NOT transmit the next message until the current transmission to the Message_Bridge completes

### Requirement 8: Message Protocol Format

**User Story:** As a developer, I want a canonical message envelope over the bridge, so that Message_Type, Correlation_ID, and payload are unambiguously encoded and decoded on both sides.

#### Acceptance Criteria

1. THE Message_Bus SHALL define a canonical wire envelope as three fields separated by a single newline character (U+000A): `Message_Type \n Correlation_ID \n payload`
2. THE Message_Type field SHALL appear first, followed by the Correlation_ID field, followed by the payload field — the payload MAY itself contain newline characters
3. WHEN encoding an outbound message, THE Message_Bus SHALL concatenate Message_Type + `\n` + Correlation_ID + `\n` + payload into a single string before transmitting via the Message_Bridge
4. WHEN decoding an inbound message, THE Message_Bus SHALL split on the first two occurrences of `\n` to extract Message_Type (before first `\n`), Correlation_ID (between first and second `\n`), and payload (everything after second `\n`, which may contain additional `\n` characters)
5. WHEN encoding a message with no payload, THE Message_Bus SHALL transmit `Message_Type \n Correlation_ID \n` (trailing newline, empty payload)
6. WHEN encoding a message with an empty-string payload, THE encoding SHALL be identical to no-payload encoding (empty string and absent payload are equivalent on the wire)
7. THE Message_Bus SHALL produce a payload identical to the original input after a round-trip of encoding followed by decoding for any valid Message_Type, Correlation_ID, and payload combination where total encoded string length does not exceed 2,097,152 characters
8. IF the Message_Bus receives a string from the Message_Bridge that does not contain at least two newline characters, THEN THE Message_Bus SHALL discard the string and not deliver it to any Subscriber or Handler
9. THE Correlation_ID field SHALL be a non-empty string containing only alphanumeric characters and hyphens (regex: `[a-zA-Z0-9-]+`), with a maximum length of 36 characters
10. THE Message_Type field SHALL be a non-empty string containing only lowercase alphanumeric characters, hyphens, and colons (regex: `[a-z0-9:-]+`), with a maximum length of 64 characters

### Requirement 9: Migration of Existing Open-File Flow

**User Story:** As a developer, I want the existing Ctrl+O open-file communication to route through the Message_Bus, so that all messaging is unified under one service.

#### Acceptance Criteria

1. WHEN the user presses Ctrl+O (or Cmd+O on macOS), THE Frontend SHALL send an "open-file" command by calling Message_Bus.send rather than calling window.external.sendMessage directly — direct calls to window.external.sendMessage SHALL be prohibited
2. WHEN the Backend sends a file-path response through the Message_Bridge, THE Message_Bus SHALL deliver the response string to the callback registered via Message_Bus.subscribe for the "open-file" response channel
3. WHILE the Frontend is awaiting a response from a previous "open-file" command, THE Frontend SHALL not send additional "open-file" commands on subsequent Ctrl+O (or Cmd+O) key presses, and WHEN the Frontend receives a response through the Message_Bus, THE Frontend SHALL clear the awaiting state and resume accepting Ctrl+O (or Cmd+O) key presses
4. WHEN the Frontend receives an empty string response through the Message_Bus, THE Frontend SHALL retain the current Display_Area content unchanged
5. WHEN the Backend receives an "open-file" message from the Message_Bus layer, THE Backend SHALL process the command using the same native dialog flow and send the response string back through the Message_Bridge in the same format (absolute file path or empty string)

### Requirement 10: System Messages

**User Story:** As a developer, I want a dedicated system message channel for alerts and exceptions that is always processed regardless of subscriber registration, so that critical backend notifications are never silently dropped.

#### Acceptance Criteria

1. THE Message_Bus SHALL reserve all Message_Types with the prefix `"system:"` as System_Messages (e.g. `"system:error"`, `"system:alert"`)
2. System_Messages SHALL always be processed with highest urgency on the frontend: WHEN the Message_Bus_Client receives a System_Message, it SHALL deliver it to handlers before any queued non-system inbound deliveries (inbound routing priority, distinct from outbound dispatch Priority in Req 7)
3. WHEN the Message_Bus_Client receives a System_Message, THE Message_Bus_Client SHALL deliver it to any Subscribers registered for that specific system Message_Type
4. IF no Subscribers are registered for a received System_Message's Message_Type, THE Message_Bus_Client SHALL deliver the message to a dedicated system handler that is always active (not the Fallback_Handler)
5. THE Message_Bus_Client SHALL provide a method to register a default system handler at initialization time that processes all unsubscribed System_Messages
6. THE Message_Bus_Host SHALL expose a method to send System_Messages to the frontend using the `"system:"` prefix convention

### Requirement 11: Fallback Handler

**User Story:** As a developer, I want a generic catch-all handler for messages that have no subscriber, so that no non-system messages are silently lost during development or unexpected scenarios.

#### Acceptance Criteria

1. THE Message_Bus_Client SHALL allow registration of exactly one Fallback_Handler via a dedicated method
2. WHEN an Inbound_Message arrives with a Message_Type that has no registered Subscribers and is NOT a System_Message, THE Message_Bus_Client SHALL route the message (Message_Type, Correlation_ID, payload) to the Fallback_Handler
3. IF no Fallback_Handler is registered and no Subscribers exist for a non-system Message_Type, THE Message_Bus_Client SHALL discard the message and log a debug-level message indicating the discarded Message_Type and Correlation_ID
4. IF the Fallback_Handler throws an error, THE Message_Bus_Client SHALL catch the error and not propagate it
5. THE Message_Bus_Client SHALL allow replacing or unregistering the Fallback_Handler at any time

### Requirement 12: Request Lifecycle and Timeout

**User Story:** As a developer, I want pending requests to have a defined lifecycle with timeout and cleanup, so that the system does not leak memory or leave callers waiting indefinitely.

#### Acceptance Criteria

1. WHEN the Message_Bus_Client sends a request, THE Message_Bus_Client SHALL insert the Correlation_ID into a pending-requests map with the current timestamp
2. THE Message_Bus_Client SHALL support a configurable timeout duration per Message_Type (default: 30 seconds)
3. WHEN a pending request exceeds its timeout duration without receiving a matching response, THE Message_Bus_Client SHALL remove the Correlation_ID from the pending-requests map and deliver a timeout notification to the Subscriber for that Message_Type (with the Correlation_ID and a timeout indicator)
4. WHEN a response arrives with a Correlation_ID that exists in the pending-requests map, THE Message_Bus_Client SHALL remove the entry from the map and deliver the response to Subscribers
5. WHEN a response arrives with a Correlation_ID that does NOT exist in the pending-requests map and does NOT match a Backend_Push pattern, THE Message_Bus_Client SHALL discard the response (late/duplicate response after timeout or unknown ID)
6. THE Message_Bus_Client SHALL expose a method to cancel a pending request by Correlation_ID, removing it from the pending-requests map without delivering any notification — the method SHALL both exist and functionally remove the entry such that subsequent responses for that Correlation_ID are discarded
7. WHEN a "latest-wins" queue discards a queued message, THE Message_Bus_Client SHALL also remove that message's Correlation_ID from the pending-requests map (the request was never sent, so no response is expected)

### Requirement 13: Error Policy

**User Story:** As a developer, I want a defined error handling policy for each failure mode, so that the system behaves predictably and failures are observable.

#### Acceptance Criteria

1. IF the Message_Bridge throws an error during outbound transmission, THEN THE Message_Bus_Client SHALL discard the message, log the error to the console, emit a structured error event to the error stream, and leave the Correlation_ID in the pending-requests map so that the timeout fires naturally — the Correlation_ID SHALL NOT be removed from the pending-requests map on bridge error
2. IF the Message_Bus receives a string that fails protocol parsing (fewer than two newlines, invalid Message_Type format, invalid Correlation_ID format), THEN THE Message_Bus SHALL discard the string and log a warning to the console
3. IF a Message_Bus_Host Handler throws an exception during request processing, THEN THE Message_Bus_Host SHALL catch the exception, log it, and send a System_Message of type `"system:error"` to the frontend with the Correlation_ID of the failed request and the error description as payload
4. IF the Message_Queue for a Message_Type overflows (accumulate mode, 100-message cap), THEN THE Message_Bus_Client SHALL discard the newest message and log a warning to the console
5. IF a Subscriber or Fallback_Handler throws an error during inbound message processing, THEN THE Message_Bus_Client SHALL catch the error, log it to the console, and continue processing remaining Subscribers
6. THE Message_Bus SHALL NOT implement automatic retry for any failure — all failures are fire-once-discard with logging
7. THE Message_Bus_Client SHALL expose an observable error stream that emits structured error events (error type, Message_Type, Correlation_ID, description) for external monitoring

### Requirement 14: Host Handler Concurrency

**User Story:** As a developer, I want defined concurrency guarantees on the backend handler execution, so that I know whether handlers can run in parallel and what ordering is guaranteed.

#### Acceptance Criteria

1. THE Message_Bus_Host SHALL process incoming messages sequentially in the order they arrive from the Message_Bridge — it SHALL NOT invoke multiple Handlers concurrently
2. WHEN a Handler is invoked, THE Message_Bus_Host SHALL await its completion (if async) before processing the next message from the bridge
3. IF a Handler performs long-running work, THE Handler MAY offload work to a background task and MAY send intermediate status updates with different Correlation_IDs, but the final response SHALL be sent via the Message_Bus_Host's send method with the original Correlation_ID
4. THE Message_Bus_Host SHALL guarantee that for messages of the same Message_Type, Handlers are invoked in the order the messages were received from the bridge
5. THE Message_Bus_Host SHALL NOT impose ordering guarantees across different Message_Types beyond the sequential processing order

### Requirement 15: Message Validation

**User Story:** As a developer, I want message fields validated on both sides, so that malformed messages are rejected early and don't cause downstream failures.

#### Acceptance Criteria

1. THE Message_Type field SHALL conform to the pattern `[a-z0-9:-]+` with a maximum length of 64 characters — messages with non-conforming Message_Type SHALL be rejected
2. THE Correlation_ID field SHALL conform to the pattern `[a-zA-Z0-9-]+` with a maximum length of 36 characters — messages with non-conforming Correlation_ID SHALL be rejected
3. THE payload field SHALL be a string with a maximum length of 2,097,152 characters (2 MB) — messages exceeding this limit SHALL be rejected
4. THE Message_Bus_Client SHALL validate outbound messages before enqueuing — if validation fails, the send method SHALL throw an error to the caller (not silently discard)
5. THE Message_Bus_Host SHALL validate inbound messages after parsing — if validation fails, the message SHALL be discarded and a warning logged
6. THE Message_Bus_Host SHALL validate outbound responses and Backend_Push messages before encoding — if validation fails, the send SHALL throw an exception to the Handler
7. THE Message_Bus_Client SHALL validate inbound messages after parsing — if validation fails, the message SHALL be discarded and a warning logged

### Requirement 16: Capacity Constraints

**User Story:** As a developer, I want explicit capacity limits for all queue modes, so that resource usage is bounded and predictable.

#### Acceptance Criteria

1. FOR "accumulate" Queue_Mode, THE Message_Bus_Client SHALL enforce a maximum of 100 messages per Message_Type queue
2. FOR "latest-wins" Queue_Mode, THE Message_Bus_Client SHALL enforce a maximum of 1 message per Message_Type queue (by definition of the mode)
3. THE pending-requests map SHALL enforce a maximum of 1000 concurrent pending requests across all Message_Types — if exceeded, THE Message_Bus_Client SHALL reject the send call and throw an error
4. THE Message_Bus_Client error stream (Req 13.7) SHALL have no capacity limit and SHALL emit events as they occur
