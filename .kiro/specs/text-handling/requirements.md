# Requirements Document

#[[file:.kiro/specs/_global/requirements-shared.md]]

## Introduction

Text Handling feature. After a file is opened (tab created), the backend starts scanning and waits 500ms before responding with an initial text view (rows up to viewport dimensions). The frontend displays this initial view immediately. When the full scan completes, the backend pushes a "scan-complete" notification, and the frontend sends a new "get-view" request to refresh the display with fully-scanned data.

Each opened file gets a unique View_Session_ID (UUID) generated by the backend. The same file can be opened in multiple tabs simultaneously — each tab has its own independent session and FileViewService instance. All communication (get-view, scan-complete, close-file) uses View_Session_ID as the key, not file path.

The flow has two phases: (1) an initial view delivered proactively by the backend after a 500ms scan delay as part of the open-file response, and (2) a refresh triggered by the scan-complete notification where the frontend sends a separate "get-view" request to obtain the fully-indexed content.

## Glossary

- **Text_View_Area**: The main content region of the UI Shell displaying file content or the empty-state prompt
- **View_Session_ID**: A unique identifier (UUID) generated by the backend when a file is opened, associating a tab with its FileViewService instance; allows the same file to be opened in multiple tabs independently
- **Char_Metrics**: Measured pixel width and height of a single monospace character within Text_View_Area, used to compute row and column counts
- **Row_Count**: Number of text rows that fit vertically in Text_View_Area, derived from area pixel height divided by Char_Metrics height (floored)
- **Col_Count**: Number of text columns that fit horizontally in Text_View_Area, derived from area pixel width divided by Char_Metrics width (floored)
- **View_Request**: A "get-view" message sent from frontend to backend containing View_Session_ID, startLine, startCol, rowCount, colCount
- **View_Response**: The backend response to a View_Request containing a newline-delimited list of row strings representing the viewport content
- **Initial_View**: The text view data (rows up to viewport dimensions) sent proactively by the backend after a 500ms scan delay as part of the open-file response flow, before the full scan completes
- **Scan_Complete_Notification**: A "scan-complete" message pushed from backend to frontend indicating the full file scan has completed for a given View_Session_ID; triggers a refresh request from the frontend
- **Get_View_Handler**: The backend message handler registered for "get-view" messages that invokes FileViewService.GetViewAsync

## Requirements

### Requirement 1: Text View Area Measurement

**User Story:** As a user, I want the application to automatically determine how many rows and columns of text fit in the viewing area, so that the correct amount of content is requested from the backend.

#### Acceptance Criteria

1. WHEN Text_View_Area is rendered with an active tab, THE Text_View_Area component SHALL measure the available pixel width and height of its content region (the element's client area excluding borders and scrollbars)
2. THE Text_View_Area component SHALL compute Char_Metrics by rendering a single reference character ("M") in an off-screen element using the same monospace font-family and font-size applied to file content display, and measuring its bounding width and height in pixels
3. THE Text_View_Area component SHALL compute Row_Count as floor(available pixel height / Char_Metrics height), with a minimum value of 1; IF Char_Metrics are not available (e.g., measurement element not yet rendered), THEN THE component SHALL fall back to the minimum value of 1 for Row_Count
4. THE Text_View_Area component SHALL compute Col_Count as floor(available pixel width / Char_Metrics width), with a minimum value of 1; IF Char_Metrics are not available (e.g., measurement element not yet rendered), THEN THE component SHALL fall back to the minimum value of 1 for Col_Count
5. WHEN the Text_View_Area is resized (window resize or layout change such as tab position toggle), THE Text_View_Area component SHALL recompute Row_Count and Col_Count from the new dimensions after a debounce period of 150 milliseconds from the last resize event
6. WHEN Row_Count or Col_Count changes after computation or recomputation, THE Text_View_Area component SHALL emit the new Row_Count and Col_Count values as an observable output (signal or event) so that consuming components can request updated content from the backend
7. WHILE no active tab exists in Tab_Container, THE Text_View_Area component SHALL skip the entire measurement pipeline (including pixel dimension measurement and character metrics computation) and SHALL NOT emit Row_Count or Col_Count values

### Requirement 2: View Request Trigger

**User Story:** As a user, I want the file content to appear automatically after a file is opened and scanned, so that I do not need to take any additional action to see the file.

#### Acceptance Criteria

1. WHEN the frontend receives an Initial_View from the backend (as part of the open-file response flow), THE frontend SHALL render the received rows in the Text_View_Area for the corresponding tab immediately without waiting for a Scan_Complete_Notification
2. WHEN a Scan_Complete_Notification is received for the active tab's View_Session_ID AND Row_Count and Col_Count have been computed, THE frontend SHALL send a View_Request via Message_Bus with View_Session_ID, startLine=0, startCol=0, and the current Row_Count and Col_Count to refresh the display with fully-scanned data
3. THE frontend SHALL send the refresh View_Request as a separate "get-view" message via Message_Bus_Client, independent of the "open-file" message flow
4. IF Row_Count or Col_Count have not yet been computed when the Scan_Complete_Notification arrives, THEN THE frontend SHALL defer the refresh View_Request until measurement completes; IF the active tab changes before measurement completes, THEN THE frontend SHALL cancel the deferred request for the previously active tab
5. IF a View_Request is already pending for the active tab (awaiting response), THEN THE frontend SHALL not send a duplicate View_Request for the same tab
6. WHEN Row_Count or Col_Count change due to a resize event AND a Scan_Complete_Notification has been received for the active tab's View_Session_ID, THE frontend SHALL send a new View_Request with the updated Row_Count and Col_Count for the active tab, subject to the duplicate-suppression rule in criterion 5
7. IF the active tab is closed while a View_Request is pending or deferred for that tab, THEN THE frontend SHALL cancel the pending request and not process any subsequent response for that tab's View_Session_ID

### Requirement 3: Scan Complete Notification

**User Story:** As a user, I want the backend to notify the frontend when the full file scan is done, so that the frontend can refresh the view with fully-indexed data.

#### Acceptance Criteria

1. WHEN FileViewService scan reaches FullScanComplete state for a session, THE backend SHALL send a "scan-complete" message via Message_Bus to the frontend with the View_Session_ID as payload
2. THE backend SHALL send each Scan_Complete_Notification as a Backend_Push via Message_Bus_Host without requiring a prior request from the frontend
3. THE frontend SHALL subscribe to "scan-complete" messages on Message_Bus_Client and associate received notifications with the corresponding tab by matching the View_Session_ID in the payload to the tab's stored View_Session_ID; WHEN a matching notification is received, THE frontend SHALL initiate a refresh View_Request per Requirement 2 criteria
4. IF a "scan-complete" message is received with a View_Session_ID that does not match any currently open tab, THEN THE frontend SHALL discard the notification without error; discarding a notification SHALL NOT prevent the frontend from initiating View_Requests for other sessions or for the same session if a matching tab is subsequently opened
5. THE Message_Bus_Client SHALL configure the "scan-complete" message type with accumulate queue mode so that notifications are delivered reliably

### Requirement 4: Get View Backend Handler

**User Story:** As a developer, I want a backend handler that processes view requests and returns file content rows, so that the frontend can display file content.

#### Acceptance Criteria

1. WHEN a "get-view" message is received by the backend, THE Get_View_Handler SHALL parse the payload to extract View_Session_ID, startLine, startCol, rowCount, and colCount per the format defined in Requirement 6
2. THE Get_View_Handler SHALL locate the FileViewService instance associated with the requested View_Session_ID (created during the open-file flow); IF no instance exists, THEN return an error response prefixed with "ERROR:" indicating the session is not found
3. THE Get_View_Handler SHALL invoke FileViewService.GetViewAsync with the extracted startLine, startCol, rowCount, and colCount parameters and the request's CancellationToken
4. WHEN FileViewService.GetViewAsync returns a successful ViewResult, THE Get_View_Handler SHALL encode the ViewResult rows as a newline-delimited string (stripping line-ending delimiters from each row) and send the response back via Message_Bus
5. IF FileViewService.GetViewAsync returns a ViewError (even when a ViewResult is also present), THEN THE Get_View_Handler SHALL return an error response prefixed with "ERROR:" followed by the ViewError message; the error response takes priority over any successful ViewResult
6. IF the payload cannot be parsed (wrong field count or non-integer numeric values), THEN THE Get_View_Handler SHALL return an error response prefixed with "ERROR:" indicating the parse failure with the specific invalid field name

### Requirement 5: View Response Display

**User Story:** As a user, I want to see the file content rendered in the text viewing area after the view is loaded, so that I can read the file.

#### Acceptance Criteria

1. WHEN a successful View_Response is received for the active tab's View_Session_ID, THE Text_View_Area component SHALL render the row strings as visible text content using a monospace font-family, with each row string displayed verbatim (no character additions or removals), regardless of whether a View_Request is currently marked as pending
2. THE Text_View_Area component SHALL render each row string as a separate block-level element (one element per row), preserving the array order received from the backend (first row at top, last row at bottom)
3. THE Text_View_Area component SHALL set overflow to hidden on the content container so that no horizontal or vertical scrollbars appear for the rendered view (content fits within measured dimensions by construction of Row_Count and Col_Count)
4. IF an error View_Response is received correlated to the active tab's pending View_Request, THEN THE Text_View_Area component SHALL display the error description (payload after the "ERROR:" prefix) in place of file content for the active tab, rendered in a visually distinct manner from normal file content
5. WHEN the active tab changes to a tab that already has loaded view rows, THE Text_View_Area component SHALL display that tab's cached view rows synchronously (within the same change detection cycle, without sending a new View_Request or awaiting any asynchronous operation); IF the cached rows reference is present but contains no actual row data, THEN THE component SHALL fall back to displaying an empty content region (no empty-state prompt) rather than rendering an empty or invalid view
6. WHILE a View_Request is pending for the active tab and no previously cached view rows exist for that tab, THE Text_View_Area component SHALL display no file content (empty content region, no empty-state prompt)

### Requirement 6: View Request Payload Format

**User Story:** As a developer, I want a well-defined payload format for view requests, so that frontend and backend can communicate unambiguously.

#### Acceptance Criteria

1. THE View_Request payload SHALL be formatted as a newline-delimited string (delimiter: U+000A) with exactly five fields in order: View_Session_ID, startLine, startCol, rowCount, colCount; the View_Session_ID field SHALL NOT contain newline characters (U+000A)
2. THE startLine, startCol, rowCount, and colCount values SHALL be encoded as decimal integer strings containing only ASCII digits 0-9 with no leading zeros except for the value "0" itself, no whitespace, and no sign characters; values SHALL be within the range 0 to 2,147,483,647
3. IF the payload does not contain exactly five newline-delimited fields, THEN THE Get_View_Handler SHALL return an error response prefixed with "ERROR:" indicating the payload structure is invalid
4. IF any of the four numeric fields (startLine, startCol, rowCount, colCount) cannot be parsed as a valid decimal integer within range, THEN THE Get_View_Handler SHALL return an error response prefixed with "ERROR:" indicating which field is invalid
5. THE View_Response payload for a successful result SHALL be the row strings joined by newline characters (U+000A); the Get_View_Handler SHALL strip line-ending delimiters from each ViewResult row before joining
6. THE View_Response payload for an error SHALL be a single string beginning with the prefix "ERROR:" (exactly six characters: E, R, R, O, R, colon) followed by the error description; the frontend SHALL treat any response beginning with "ERROR:" as an error response

### Requirement 7: FileViewService Instance Management

**User Story:** As a developer, I want FileViewService instances to be created when files are opened and available for subsequent view requests, so that the scan runs once and views are served from the indexed file.

#### Acceptance Criteria

1. WHEN the "open-file" handler successfully opens a file (non-empty path returned), THE backend SHALL generate a unique View_Session_ID (UUID), create a FileViewService instance for that file path passing a CancellationToken tied to the application lifetime, and store the instance in a View_Session_ID-keyed collection for later retrieval
2. THE backend SHALL return the View_Session_ID to the frontend as part of the "open-file" response payload (alongside the file path and initial view rows) so the frontend can associate the tab with its session
3. THE backend SHALL associate each FileViewService instance with its View_Session_ID so that "get-view" requests can locate the correct instance by exact ID match; multiple sessions MAY reference the same file path (same file opened in multiple tabs)
4. IF a "get-view" request references a View_Session_ID with no associated FileViewService instance, THEN THE Get_View_Handler SHALL return an error response indicating the session is not found
5. WHEN a "close-file" message is received by the backend with a View_Session_ID, THE backend SHALL dispose the associated FileViewService instance and remove it from the session-keyed collection; IF the disposal operation fails (e.g., instance is in an active state), THEN THE backend SHALL proceed with removal from the collection regardless, ensuring the session is cleaned up
6. IF a "close-file" message references a View_Session_ID with no associated FileViewService instance, THEN THE backend SHALL ignore the message without returning an error
7. WHEN a tab is closed on the frontend, THE frontend SHALL send a "close-file" message to the backend with the tab's View_Session_ID as payload

### Requirement 8: Initial View After Open

**User Story:** As a user, I want to see file content immediately after opening a file without waiting for the full scan to complete, so that the application feels responsive.

#### Acceptance Criteria

1. WHEN the "open-file" handler creates a FileViewService instance and starts the scan, THE backend SHALL wait 500 milliseconds before responding to the open-file request, allowing the scan to make initial progress
2. AFTER the 500ms delay, THE backend SHALL invoke FileViewService.GetViewAsync with startLine=0, startCol=0, and row/column counts matching the frontend's current viewport dimensions (passed as part of the open-file request payload), and include the resulting rows in the open-file response
3. THE backend SHALL include the Initial_View rows in the open-file response payload alongside the View_Session_ID and file path, formatted so the frontend can parse and display them immediately
4. WHEN the frontend receives the open-file response containing Initial_View rows, THE frontend SHALL render those rows in the Text_View_Area for the new tab immediately without waiting for a Scan_Complete_Notification or sending a separate View_Request
5. IF the scan has not yet reached a state where GetViewAsync can return data after the 500ms delay, THEN THE backend SHALL return an empty Initial_View (zero rows) and the frontend SHALL display an empty content region until the Scan_Complete_Notification triggers a refresh
6. IF the viewport dimensions are not yet available when the open-file request is sent, THEN THE frontend SHALL send default dimensions (a reasonable fallback such as 40 rows and 120 columns) so the backend can produce an Initial_View
7. WHEN the frontend subsequently receives a Scan_Complete_Notification for the same View_Session_ID, THE frontend SHALL send a refresh View_Request per Requirement 2 to replace the Initial_View with fully-scanned content
